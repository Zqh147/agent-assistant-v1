# 设计说明

记录主要设计决策与取舍。实现细节以 README 和源码为准。

## 职责划分：模型与程序

LLM 负责理解意图、选择工具和组织回答；订单记录、日期窗口、资格判断、工单状态和提交权限都由 Python 与 SQLite 决定。即使模型直接请求提交工单，工具仍会检查当前轮用户确认、客户归属、创建会话、资格和规则版本。

产品手册 / FAQ 只用于回答设备操作问题，演示售后规则只用于判断申请资格。两类资料分开存放和标注，不会用配置手册去推断保修政策。

## 工单：先草稿后提交

工单先保存为 `draft`，让用户核对订单、申请类型和问题描述，再由用户在下一轮明确回复「确认提交」才变为 `submitted`。

- 确认由 `graph.py` 在调用模型**之前**根据原始用户消息判定，模型无法通过传参伪造。
- 同一客户 / 会话 / 订单 / 申请类型使用唯一草稿键，重复准备复用原工单。
- 提交在事务中完成并检查状态，重复提交不会重复写入事件。
- 业务写工具同步执行，超时后不自动重试，避免重复写入；检索是读操作，保留超时与有限重试。

## 会话与业务上下文持久化

SQLite 保存已完成的对话轮次和业务上下文（订单、设备范围、待确认工单）。业务工具一完成就保存上下文，因此即使之后模型回复失败，已保存的草稿仍能在原会话中继续。旧会话表通过增加一列迁移，不清空历史。完整的图节点检查点仍是 `InMemorySaver`。

## 检索集成

已查询订单的设备范围（型号、硬件版本、地区）会自动补入检索参数；模型传入冲突参数时拒绝执行。技术问题与订单指令分开检索，避免把「查订单 + 技术问题」整段送入检索后，因相关性阈值而误拒绝技术证据。

## 工具接入方式

- MCP 计算 / 时间工具：stdio 子进程，启动时通过 `tools/list` 动态发现。
- 售后业务工具：本地执行，以便由服务端注入客户与会话上下文。
- 产品知识检索：本地 Python 适配器，通过 HTTP 调用 RAG 检索服务（不是 MCP）。

## 常见问题

**为什么用 LangGraph，而不是一个 while 循环？**
while 循环也能实现 Agent。LangGraph 把状态、节点和条件路由显式化，便于增加步数上限、执行记录和持久化等横切逻辑。它不替代工具函数、schema 或模型本身。

**MCP 与 Function Calling 是什么关系？**
Function Calling 描述模型请求调用哪个工具、用什么参数；MCP 负责客户端与工具服务之间的发现、通信和调用。模型只看到 schema，实际的 MCP 请求由程序发起。

**`plan` 是预先规划的吗？**
不是。它根据模型实际产生的 `tool_calls` 增量添加步骤，再按执行结果更新状态，是执行记录而非任务分解器。独立的任务分解与重规划尚未实现。

**如何确认模型没有"假装"调用工具？**
核对 trace 中的来源、状态和 `call_id`，并与 `plan` 对应；在线评估同时检查答案与工具行为。trace 是程序记录的执行路径，需结合实现与 MCP 集成测试一起看。

**工具超时能终止正在执行的工具吗？**
线程超时只是停止等待，无法强制终止已经运行的 Python 线程。MCP 适配器另有异步超时与会话清理；更强的隔离与硬终止需要进程级设计。

**验收 100% 通过说明什么？**
只说明有限的验收用例在该次运行中满足检查规则。离线脚本模型不评估理解能力，在线验收用例也不代表真实业务准确率。
